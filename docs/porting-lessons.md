# 三款游戏的移植经验与共用边界

本页总结《王国之泪》《星之卡比 新星同盟》和《恶魔城：贝尔蒙特的诅咒》的现有证据。三者都让改写后的 ARM64 游戏模块在 Apple 芯片上直接执行，由宿主提供 Switch 服务并以 Metal 呈现 NVN 绘制；它们的完成度并不相同。本页所说的“共用”指可复用的源码与验证方法，不表示三款游戏已经使用同一个完整构建入口，也不表示已通过全游戏验收。

| 游戏 | 已验证的范围 | 目前的交付入口 | 仍需隔离的差异 |
|---|---|---|---|
| 王国之泪 | 1.0.0、1.1.2、1.4.3 的打包与所记录的场景测试 | 根目录 `build_app.py` 从玩家 XCI/NSP 和可选更新生成 App | 版本哈希、RomFS 叠层、共享字体、首启着色器集合、存档升级备份及游戏指令补丁 |
| 星之卡比 | 基础版预览的菜单、前两关入口、存档读回和部分画面/节拍测试 | `games/kirby/package_preview.py` 打包项目外已验证宿主 | 外部宿主补丁、SDK 指令站点、资源语言映射、预览启动参数；尚无一键输入游戏包的构建入口 |
| 恶魔城 | 主游戏 1.1.0 的设置、序章影片、关卡移动、首次存档，以及 2026-10-22 的隔离死亡复验 | `games/castlevania/build_app.py` 打包项目外已验证镜像与两份 DLC | 主模块间接跳转、Unity 资源问题、H.264 路径、DLC 身份与场景后处理适配；刷怪长帧与未游玩的关卡仍需验证 |

## 可复用的移植流程

1. **先证明输入身份。** 从 XCI/NSP 中按 title ID 选择 Program、Control 和 RomFS；更新包只与同一基础 title 合并。核对模块、RomFS 哈希链、大小、版本及必要的工具哈希。未知构建必须停止，不能靠文件名或游戏画面猜版本。组合 XCI 和 DLC 的发现说明 title ID 选择应属于容器层，而非某个游戏打包脚本。
2. **把代码改写与客体补丁分开。** NSO 解析、重定位、指令门和模块装载是共用机制；写死的偏移、原指令、目标集合及构建号是游戏版本的证据。卡比 SDK 的 HID 站点和恶魔城的间接尾跳转都需要先核对原值，再应用定点改写；不能将一个游戏的偏移变成通用规则。
3. **以服务语义修复宿主。** 文件系统、时钟、输入、音频和 NVN 接口优先按接口本身实现。若修复只因某款游戏暴露了错误，例如 NVN 的阶段掩码，应先做独立的语义测试，再考虑推广到所有游戏。不能把尚未验证的异常路径直接推广。
4. **把图形与媒体的证据分层。** 着色器翻译、管线创建、提交和最终窗口呈现分别观察；纹理原始内容与玩家窗口截图可能不同。卡比的 UI 坐标、恶魔城的 sRGB 输出及场景后处理都说明“能看到一帧”不足以证明整条绘制链正确。影片还要分别检查画面、音轨、结束回调和正常节奏。
5. **先做可复现的最小探针，再测真实游玩。** 无游戏数据的合成容器与纯函数测试保护通用逻辑；指令等价、GPU `probe-gfx` 和隔离存档运行验证更深一层。每项结论只覆盖它实际经过的版本、场景与持续时间，不能把局部性能数字写成全游戏保证。
6. **保持可重建和可回退。** 输出 App、解包数据、着色器种子、日志和测试存档放在项目外；正式存档与测试档分离。已验证的输入、派生文件和预热包在打包前核对哈希。替换正式 App 前先完成签名和 `--check`，保留现有可运行包直到替换条件满足。

阶段掩码调查可在隔离运行中设置 `TOTK_BINDPROG_LOG=<起始帧>-<结束帧>`，再用 `games/totk/scripts/analyze_nvn_bindings.py <项目外日志>` 离线统计掩码、空绑定和部分图形绑定。该日志最多输出 20,000 条记录，且不包含每个着色器的阶段身份；统计只能说明采样窗口实际出现过什么，不能直接证明另一款游戏支持同样的程序组合。

运行时现在把图形和计算程序分成两个状态槽。恶魔城宿主沿用已验证的掩码默认与 `CASTLEVANIA_MASKED_BIND=0` 负对照；其他配置须显式设置 `DM_NVN_STAGE_BIND=1` 才试用新路径。源码探针和编译检查不代替真实关卡及派发结果验收；单独顶点/片元程序合成、几何和细分阶段仍未支持。

统一入口的 `inspect` 可对本体与独立更新包进行只读代码身份检查；[六份跨游戏输入的检查矩阵](generic-input-matrix.md)记录了王国之泪、卡比、恶魔城及马里奥惊奇的实际结果。马里奥的 `unported_title` 是准确的待适配状态；静态导入数量不能用作宿主能力或性能结论。

容器/ExeFS、RomFS 提取与索引、BKTR 升级档合并、NSO 盘点和静态依赖图的实现已移到根目录 `game_tools/`；王国之泪原脚本路径为薄兼容入口。共用 BKTR 入口要求显式 title ID，旧王国之泪入口保留默认值。检查器直接使用共用代码分析工具，尚不提取 RomFS；此前的马里奥本体与更新包、卡比本体、恶魔城组合 XCI 主游戏代码输入复验仍是有效基线。RomFS 的共用命令通过合成 NSP 的完整 IVFC 校验，马里奥本体的真实 RomFS 提取及升级档 BKTR 合并也已在项目外通过六层 IVFC 验证；它们仍不代表原生运行验证。此项只调整离线工具组织，不影响游戏进程的每帧或每次绘制路径。

[马里奥惊奇的第四样本](mario-wonder-input-probe.md)验证了容器、ExeFS 和 NSO 盘点的可复用部分，也暴露了固定要求 `subsdk0` 的工具假设；它尚未进入上述三款游戏的移植或交付范围。

## 这次代码收敛的位置

`packaging_common.py` 现在集中提供项目外路径检查、流式 SHA-256、普通文件校验和“同卷尝试 APFS 克隆，失败则复制”的操作。三个打包入口共用路径与复制规则，王国之泪和恶魔城也使用其中的哈希操作。路径检查会解析父目录符号链接；文件校验拒绝符号链接。卡比把预览包放到另一卷时不再依赖 `cp -c` 成功。各入口继续负责自己的资源清单、版本判断、启动器、签名时机和玩家数据目录。

这是一条较窄的共用边界。当前 `games/totk` 的宿主中仍有恶魔城编译分支，卡比仍使用外部补丁。卡比补丁针对宿主提交 `f5cc1519c5c6aed8b21c20317a9cee15f3f6d746`，其源码准备命令和测试都固定该基线；直接应用到后来的 `HEAD` 会因相同文件已改动而失败。将这些运行时差异收敛，需要先让三款游戏的同一服务或 NVN 语义在探针与实机中都成立；现在不能据打包脚本的共用就声称运行时已经通用。后续优先按以下顺序处理：阶段掩码等接口语义、启动配置与资源路径、各游戏定点补丁的独立登记。每推广一处，都要保留原游戏的负对照或原值检查，并复验受影响的游戏。

源码目录只保存本项目源码、必要依赖、测试和结论。完整工作目录放在游戏文件旁的 `TOTK_build` 或显式 `--work` 所指的项目外目录；打包候选 App 使用外部 `apps`，安装后的恶魔城正式 App 位于 `/Applications`，开发缓存使用外部 `development`，隔离测试数据在验证时进入各游戏用户数据目录的 `tests` 子目录，结束后按日期归档到项目外。历史证据位置和具体复验方法见各游戏 README、[1.4.3 记录](v1.4.3-port.md)、[着色器首启记录](first-launch-shaders.md)与[音频排障](audio-troubleshooting.md)。
