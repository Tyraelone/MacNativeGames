# NVN 图形与计算程序状态分离：受控增量

## 问题

当前 Metal 回放层用 `S.prog` 同时代表图形程序和计算程序。恶魔城的 `0x3` 非空绑定后跟空 `0x3c` 已用专用规则保留图形程序，但若把这条规则直接推广给所有游戏，空 `0x20` 也会保留已经需要清除的计算程序。写回索引中的 `g_pp_prog` 同样混用绘制与派发的程序。只修改回放、忽略前瞻，会让附件读写判断失去一致性。

## 范围与接口

在宿主状态中保留图形与计算两个程序指针。开启分离模式时，含顶点/片元位的绑定更新图形指针，含计算位的绑定更新计算指针；未选中的一侧保持。提交前瞻也保存两个指针，绘制读取图形指针，派发读取计算指针。回放与图形前瞻共用同一绑定判定函数。

深度/模板附件前瞻跟踪图形程序，只在绘制时判断片元深度输出；计算绑定不改变该判断。计算阶段诊断记录使用计算程序指针。

恶魔城配置默认开启，`CASTLEVANIA_MASKED_BIND=0` 继续提供旧行为负对照。其他配置默认保持旧行为，可设置 `DM_NVN_STAGE_BIND=1` 显式试验；该变量若设置则优先于恶魔城旧变量。这样源码层提供可复验的双通道实现，同时不在未完成实机验证时改变其他游戏的默认行为。

此增量仅处理“顶点与片元作为一个图形程序”和“计算程序”两条通道。仅顶点或仅片元的绑定需要程序合成，几何/细分着色器还没有翻译路径；出现这些组合时不能宣称已支持。离线绑定分析器负责指出部分图形绑定，启用前还需检查程序真实阶段身份。

## 性能与验证

每次 `BindProgram` 执行两次位检查；仅计算程序变化时只将计算参数表标脏，图形程序变化才标记图形管线与全部参数表。绘制热路径继续直接读图形指针，计算派发直接读计算指针。不新增每次绘制的程序组合、哈希或缓存查找。纯 C 探针覆盖图形、计算、空绑定和旧行为；Metal 源文件用普通与恶魔城配置分别做语法检查。真实 App 的关卡画面、无程序绘制计数、冷/热缓存帧时间、管线创建数量及内存仍须在项目外隔离工作区复验。没有这些实机证据，其他游戏的开关不得默认开启。
