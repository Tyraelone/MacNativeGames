# 通用构建入口：第一阶段设计

## 目的与边界

项目最终要用同一套经过验证的宿主源码、容器处理和打包流程支持多款游戏，同时保持原生 ARM64 运行与 Metal 热路径的性能。本阶段先建立可信的统一入口和明确的支持状态，供后续逐项收敛运行时语义使用。

本阶段交付一个 `build_game.py` 命令，接受三个明确的目标：

- `totk`：从用户的 XCI/NSP 及可选更新构建正式 App，沿用根目录 `build_app.py` 的参数和版本校验。
- `kirby-preview`：封装已经在项目外准备、验证并编译的卡比宿主，沿用 `games/kirby/package_preview.py` 的参数。此入口不宣称可从 NSP 一步构建。
- `castlevania`：封装项目外已验证的 1.1.0 工作目录及可选着色器种子，沿用 `games/castlevania/build_app.py` 的参数。此入口不宣称可从原始 XCI 一步构建。

`list` 显示每个目标的 title ID、成熟度和实际入口条件。未知目标报错，不根据文件名猜测游戏或版本。原有三个入口继续可用；新命令仅分派到这些入口，不绕过它们的身份校验、外部路径检查、签名、资源清单或回退规则。

## 决策

选用薄入口与静态目标目录，不在第一阶段搬迁大量运行时或复制三个构建器的参数解析。每个目标通过固定的源码相对路径分派；用户参数原样传给原入口，子进程退出码原样返回。命令不经 shell，避免参数重新解释。统一入口本身不创建 App、解包数据或缓存。

这一阶段的“通用”只指用户入口和目标目录。后续阶段才逐项统一 Horizon/NVN 服务语义、版本配置、补丁登记及封装流程。未知版本不能因为进入同一命令而获得支持。

## 接口与数据流

```text
build_game.py list
build_game.py totk <原 build_app.py 参数>
build_game.py kirby-preview <原 package_preview.py 参数>
build_game.py castlevania <原 build_app.py 参数>
```

入口解析目标名，读取只读目录，调用当前 Python 解释器执行对应脚本。原脚本正常退出时原样返回退出码；由信号终止时返回常见 shell 状态 `128 + 信号编号`。顶层 `--help` 显示各目标条件；目标后的 `--help` 交给原脚本。缺少目标或未知目标以非零退出，并展示可用目标。目标目录使用不可由命令行修改的源码路径，不接受外部脚本路径。

## 兼容性与性能

已有三个入口的默认参数、生成目录、签名及数据位置不变。分派器只在构建时运行，不进入游戏进程；不新增逐帧、逐绘制或逐 IPC 判断。后续运行时收敛时保持同一原则：构建期确定版本和补丁，启动期确定可用能力，热路径执行已选定实现。

## 验证

无游戏数据测试覆盖目标清单、目标及参数的精确分派、子进程退出码、未知目标与帮助转交。测试使用项目外临时脚本或纯函数检查，不生成 App。运行现有 Python 测试全集，以确保原入口与路径约束未受影响。真实游戏打包和 GPU 性能留给改变相应构建或运行时行为的后续阶段，不能从本阶段的测试推断其通过。

## 下一阶段接口

下一步将把目标目录扩展为经过校验的版本配置，并在相同入口增加只读 `inspect` 报告；报告要区分已支持版本、缺失的服务/NVN/媒体能力和未知指令改写。运行时通用化先处理已能证明的接口语义，再把游戏定点补丁独立登记。每次推广都用三款游戏的合成探针和实机基线复验，包括冷/热缓存帧时间分布、长帧和长期内存。
